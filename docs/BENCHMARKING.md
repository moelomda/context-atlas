# Context Atlas benchmarking

Context Atlas uses deterministic synthetic repositories to measure public CLI workflows without downloading external source or touching developer-owned repositories. Benchmark results are evidence about one named configuration and environment; they are not a universal production-scale claim or service-level objective.

## Safety boundary

Generated fixtures live under the operating system temporary directory:

```text
<context temporary directory>/context-atlas-benchmarks-v1/<scenario>/repo
```

Cleanup is refused unless both the path boundary and scenario marker match. The harness never deletes or initializes the repository that contains Context Atlas. An explicit `--output` path is the only supported write outside the guarded temporary benchmark root.

Synthetic source uses fixed seeds, invalid example domains, generated package names, and deterministic dates. It must not contain private source, real credentials, customer identifiers, or copied production history.

## Commands

Build Context Atlas, generate a fixture, run the benchmark, and validate the report:

```sh
npm run build
npm run benchmark:generate -- --scenario smoke --clean
npm run benchmark -- --scenario smoke --samples 2
npm run benchmark:validate -- --file <report-path>
```

`benchmark:generate` prints the fixture manifest as JSON. `benchmark` prints a concise summary and writes a versioned JSON report. Without `--output`, the report is stored under the guarded scenario directory. Use `--output` only when intentionally publishing or uploading a report.

## Scenarios

| Scenario | Purpose | Default size |
| --- | --- | --- |
| `smoke` | Pull-request and installation-level benchmark contract | 80 generated source files, 12 commits, 8 components |
| `files-10k` | Tracked-file scale qualification | 10,000 generated source files |
| `history-5k` | Long-history qualification | 5,000 deterministic commits |
| `relationships-dense` | Dense workspace dependency graph | 250 components with 12 dependencies each |
| `untracked-bounded` | Untracked fingerprint-policy pressure | 5,000 untracked generated files |

Only `smoke` is intended for every pull request. The larger scenarios are local, scheduled, or release-qualification workloads and may require substantial CPU, memory, storage, and time.

## Measured workflows

The runner resets only its marked synthetic fixture, removes prior derived Atlas state, and then invokes the built CLI for:

1. cold `init` and initial synchronization;
2. one deterministic committed change followed by incremental `sync`;
3. `overview`;
4. `map`;
5. `timeline`;
6. `search`;
7. `health`; and
8. a bounded `pack` request.

Read workflows are repeated according to the scenario or `--samples`. The report records per-sample duration, p50, p95, output bytes, Git process count, and peak Node-process RSS when `/proc` is available. It also records database bytes and selected/excluded counts that can be derived from returned contracts.

Git process counts come from `GIT_TRACE2_EVENT` `start` records emitted by commands launched inside Context Atlas. Fixture-generation and runner-owned Git commands are deliberately excluded.

## Report schema v1

Every report includes:

- source commit and dirty state;
- generation timestamp;
- OS, architecture, Node.js, npm, and Git versions;
- scenario name, configuration, and SHA-256 configuration hash;
- fixture commit and tracked/untracked counts;
- all operation samples and aggregate summaries;
- database size;
- observed graph, timeline, search, and Context Pack counts; and
- explicit limitations.

`npm run benchmark:validate` fails closed when required operations, metrics, environment fields, or limitations are missing. Future regression budgets can consume the same schema without changing the fixture or measurement commands.

## Interpreting results

Compare results only when the scenario hash, source tree, runtime, architecture, and relevant runner conditions are understood. Hosted virtual-machine noise, filesystem cache state, antivirus software, thermal throttling, and concurrent load can materially affect results.

A useful performance change should include:

- before and after reports;
- the same scenario/configuration hash;
- multiple runs when the difference is small;
- an explanation of any changed output counts; and
- confirmation that correctness, freshness, privacy, and fail-closed behavior were preserved.

Do not turn the first reference baseline into a hard regression threshold. Establish budgets only after enough repeat runs exist to distinguish normal variation from meaningful regression.

## Published reference baseline

[`benchmarks/smoke-baseline.json`](benchmarks/smoke-baseline.json) is generated by the implementation qualification workflow and validated with the same schema checker. It proves that the smoke harness completed on its recorded environment. It does not qualify the larger scenarios or promise equivalent results on another machine.
